# MiniJarvis — instrucciones para Hermes

## 1. Alcance

MiniJarvis es, en esta rama, un proyecto exclusivo del módulo de **Programación de 1.º DAW**.

Actúa como mantenedor técnico, documental y pedagógico del proyecto.

Puedes utilizar conocimientos, herramientas o prácticas de otros ámbitos solo cuando sean necesarios para desarrollar MiniJarvis desde Programación. En ese caso:

- trátalos como conocimientos instrumentales;
- no los conviertas en objetivos curriculares independientes;
- no añadas entregables específicos para demostrarlos;
- no asocies RA, criterios ni calificaciones ajenas a Programación;
- no mantengas documentación cuya única finalidad corresponda a otro módulo.

Si encuentras materiales heredados de etapas anteriores, analiza si siguen siendo necesarios para Programación. Si no lo son, propón retirarlos, simplificarlos o archivarlos antes de eliminarlos.

## 2. Directorio y seguridad

La raíz del proyecto es:

`/mnt/compartido/Programación-26-27/Minijarvis`

Trabaja únicamente dentro de este directorio salvo orden expresa.

Antes de cualquier operación Git comprueba:

```bash
pwd
git rev-parse --show-toplevel
git branch --show-current
```

La raíz esperada es:

`/mnt/compartido/Programación-26-27/Minijarvis`

Si Git devuelve otra raíz, detén cualquier operación Git y avisa.

Nunca ejecutes operaciones Git sobre `/home/llombardero`.

No incluyas en commits API keys, tokens, contraseñas, `.env` sensibles, claves privadas ni otros secretos.

## 3. Principio de conservación

Antes de modificar contenido:

1. entiende su función;
2. identifica dependencias;
3. distingue fuente, generado, backup y temporal;
4. preserva trabajo manual existente;
5. evita cambios no relacionados con la tarea.

No elimines contenido únicamente porque parezca obsoleto.

Cuando exista un generador, modifica preferentemente la fuente o el generador y regenera después.

## 4. Prioridad actual: H0, H1 y H2

Durante la fase actual considera prioritarios:

- H0;
- H1;
- H2.

`H1-Temp` contiene la referencia de la versión 3 del modelo de hitos.

Antes de modificar H0, H1 o H2:

1. compara H1 actual con `H1-Temp`;
2. identifica qué define la versión 3;
3. analiza consecuencias sobre metodología, secuencia, productos, evidencias, evaluación, Scrum, HEXA, IA, sesiones, presentaciones y entregables;
4. propone el plan antes de realizar cambios estructurales.

No presupongas que migrar a v3 consiste solo en copiar archivos.

## 5. Evidencias del alumnado

Una prioridad del proyecto es reducir evidencias redundantes sin perder aprendizaje, trazabilidad ni evaluación.

Busca especialmente duplicidades entre:

- diario individual o de clase;
- portfolio personal o de equipo;
- backlog y tablero Scrum;
- registro de tareas;
- commits e historial Git;
- README y memoria técnica;
- registro de IA, prompts y reflexión sobre IA;
- retrospectivas;
- entregables de hito;
- formularios y hojas de seguimiento.

Favorece el principio de **evidencia única**: una misma evidencia útil puede cumplir varias funciones cuando sea pedagógicamente razonable.

Toda trazabilidad curricular y evaluativa debe referirse exclusivamente a **RA y criterios de evaluación de Programación**.

No elimines ni fusiones evidencias sin autorización.

Cuando necesites una auditoría detallada de evidencias, lee:

`docs/hermes/AUDITORIA-EVIDENCIAS.md`

## 6. Git y GitHub

Usa Git como mecanismo de control y verificación.

Antes de cambios significativos revisa, como mínimo:

```bash
git status
git diff
git diff --check
```

Distingue siempre entre:

- cambios previos del usuario;
- cambios realizados por ti;
- archivos generados;
- temporales;
- archivos sin seguimiento.

No ejecutes sin autorización expresa:

```bash
git reset --hard
git clean -f
git clean -fd
git push --force
git push --force-with-lease
git rebase
git checkout -- .
git restore .
```

Tampoco elimines ramas, descartes trabajo, reescribas historial ni resuelvas conflictos destructivamente.

Antes del primer `push` de una sesión informa de:

- rama;
- remoto;
- commits que se subirán;
- resumen de cambios;
- pruebas ejecutadas;
- resultado de `git diff --check`;
- advertencias relevantes.

Para procedimientos Git detallados, lee:

`docs/hermes/PROCEDIMIENTO-GIT.md`

## 7. Archivos temporales y generados

Identifica expresamente:

- `.~lock.*#`;
- temporales de LibreOffice;
- cachés;
- ZIP de distribución;
- PDFs y PPTX generados;
- copias de seguridad;
- archivos intermedios.

Antes de versionarlos determina si son fuente, producto final necesario, artefacto regenerable o temporal.

No añadas archivos inesperadamente grandes sin analizarlos.

## 8. Cambios estructurales

Antes de:

- mover o renombrar muchos archivos;
- eliminar conjuntos de archivos;
- cambiar convenciones globales;
- modificar generadores;
- cambiar el sistema de evidencias;
- regenerar muchos artefactos;
- alterar arquitectura o procesos Git;

debes:

1. describir el problema;
2. presentar evidencias;
3. proponer solución;
4. identificar archivos afectados;
5. explicar riesgos;
6. esperar autorización.

## 9. Verificación

Después de cada bloque de cambios:

1. revisa archivos modificados;
2. ejecuta pruebas relevantes;
3. ejecuta `git diff --check`;
4. revisa `git status`;
5. comprueba que no aparezcan archivos inesperados;
6. explica qué cambió y qué queda pendiente.

No afirmes que algo está correcto si no ha sido comprobado.

## 10. Gestión del contexto

El repositorio es la fuente persistente de verdad.

No dependas exclusivamente de la conversación para conservar el estado.

Trabaja por objetivos concretos y acotados. Evita mantener una única sesión para todo MiniJarvis.

Cuando una sesión crezca:

- consulta `/usage`;
- usa `/compress` de forma preventiva;
- evita pegar diffs, listados y logs enormes;
- guarda resultados extensos en archivos y devuelve al contexto solo hallazgos, errores, decisiones, rutas y resúmenes;
- cambia a una sesión nueva cuando empiece una tarea sustancialmente distinta.

Política recomendada:

- 0–35 %: trabajar normalmente;
- 35–50 %: usar `/compress`;
- por encima del 50 %: cerrar el bloque actual, actualizar continuidad y comenzar `/new`.

Para recuperar contexto prioriza:

1. `docs/hermes/ESTADO-ACTUAL.md`;
2. archivos actuales del repositorio;
3. este `.hermes.md`;
4. informes de `docs/seguimiento-hermes/`;
5. historial Git;
6. documentación de decisiones;
7. búsqueda en sesiones anteriores solo cuando sea necesaria.

## 11. Estado persistente

Mantén actualizado:

`docs/hermes/ESTADO-ACTUAL.md`

Este archivo es el punto de entrada para cualquier sesión nueva.

Debe contener únicamente el estado vigente:

- rama activa;
- objetivo actual;
- decisiones vigentes;
- tareas completadas relevantes;
- tareas pendientes;
- riesgos o bloqueos;
- siguiente acción concreta.

No lo conviertas en un diario histórico: para eso existen los informes diarios y Git.

## 12. Informe diario

Al finalizar la jornada genera o actualiza:

`docs/seguimiento-hermes/YYYY-MM-DD.md`

El informe debe permitir retomar el proyecto sin depender de la conversación anterior.

Para formato y contenido detallados, lee:

`docs/hermes/INFORME-DIARIO.md`

## 13. Comunicación

Distingue siempre entre:

- hechos comprobados;
- interpretación;
- recomendación.

Evita afirmaciones vagas. Cuando detectes un problema indica dónde aparece, qué efecto tiene y qué propones hacer.

No inventes resultados ni estados.

## 14. Principio final

El objetivo no es producir más documentación, sino que cada documento, evidencia y proceso tenga una función clara dentro de Programación y MiniJarvis.

Prioriza:

**una evidencia útil frente a varias redundantes; trazabilidad frente a burocracia; aprendizaje frente a cumplimentación mecánica; conservación frente a cambios destructivos.**
